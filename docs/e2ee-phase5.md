# ЯЧат E2EE — этап 5: обязательный защищённый контур

Этап 5 переводит существующие аккаунты и личные чаты на fail-closed протокол версии 5. Пока у обоих участников нет активного устройства версии 5, отправка нового личного сообщения блокируется: возврата к plaintext нет.

## Что шифруется

- текст, форматирование, ответы, пересылки и клиентское время создания;
- байты и исходные метаданные вложений;
- заголовок, реальный текст, маршрут, tag и клиентское время push-уведомления;
- человекочитаемый Digital ID владельца.

Контент шифруется AES-256-GCM отдельным случайным ключом сообщения. Для каждого устройства этот ключ заворачивается через X25519/X3DH, HKDF-SHA-256 и AES-256-GCM. Отправитель подписывает ciphertext, AAD и digest полного набора конвертов своим Ed25519-ключом.

## Утечка длины и forward secrecy

Сообщение дополняется случайными байтами до одного из фиксированных buckets от 512 до 65 536 байт. Сервер видит bucket и размер зашифрованного вложения, но не точную длину текста.

После первого успешного открытия клиент сохраняет ключ сообщения в локальном AES-GCM vault и удаляет использованный приватный one-time prekey. Сервер атомарно связывает публичный one-time prekey с первым message ID и допускает только идемпотентный повтор того же сообщения. Это даёт ограниченную forward secrecy для X3DH-конверта и блокирует повторное использование prekey для другого сообщения. Полноценного Double Ratchet в этой версии нет, поэтому компрометация долговременного ключа и локального cache всё ещё является существенной угрозой.

## Digital ID

При первом открытии обновлённого клиента устройство:

1. создаёт E2EE-идентичность локально;
2. получает текущий Digital ID только в одноразовом migration-ответе владельца;
3. шифрует его случайным AES-256-GCM ключом;
4. проверяет Ed25519-attestation каждого X25519 identity key и создаёт конверт для каждого активного устройства владельца;
5. подписывает vault Ed25519-ключом;
6. отправляет только ciphertext и конверты;
7. после атомарной записи vault сервер обнуляет plaintext-колонку.

Для поиска хранится HMAC-SHA-256 от нормализованного ID. Ключ HMAC находится в окружении API, а не в Supabase. Digital ID остаётся lookup-идентификатором: доступ стороннего проекта подтверждается отдельными OTP и PKCE, а проверенному проекту возвращается только scoped subject.

Новое устройство не получает старый приватный ключ. Уже доверенное устройство локально открывает существующий content key и делает rewrap для нового полного roster, не меняя ciphertext, IV или plaintext digest. Сервер принимает только такую замену конвертов; расшифровывать ID ради восстановления он не умеет. Пока доверенное устройство не выполнит rewrap, новый клиент остаётся fail-closed.

## Push

Внешний push содержит только общий заголовок, общий fallback, `/web`, непрозрачный dedup tag, одноразовый context и зашифрованный descriptor. Chat ID, message ID, user ID, sender/recipient device ID, стабильные device public keys, реальный title, body, URL и tag в транспорт не попадают. Service worker локально перебирает свои изолированные preview keys, открывает AES-GCM контейнер и только внутри получает и проверяет Ed25519 sender proof, TTL и маршрут.

Push-провайдер всё равно видит endpoint устройства, момент отправки, размер контейнера и IP-транспорт. Скрыть эти данные при обычном Web Push невозможно.

## Что видит сервер

Сервер продолжает видеть:

- факт существования аккаунта и чата;
- состав чата и зарегистрированные устройства;
- отправителя, получателя push endpoint и приблизительное время операций;
- padding bucket сообщения, количество устройств и размеры контейнеров;
- ciphertext Digital ID и серверный HMAC lookup token.

Полное сокрытие этих метаданных потребовало бы mixnet, cover traffic, private information retrieval и отдельного протокола доставки. Этап 5 этого не обещает.

## Граница доверия

Supabase хранит публичные ключи, ciphertext и конверты, но не получает приватные X25519, Ed25519, P-256 или AES-ключи. Поэтому штатная база не может расшифровать сообщения, вложения, push descriptor или Digital ID.

Ограничения:

- первая встреча ключа использует TOFU; для защиты от злонамеренного сервера при первом контакте нужен внешний safety-number или независимый transparency log;
- вредоносный JavaScript того же origin, захваченное устройство или доступ к разблокированному браузерному профилю находится вне защиты E2EE;
- старые plaintext-сообщения нельзя честно «сделать E2EE» на сервере задним числом. Их можно удалить либо переотправить клиентским backfill после подтверждения владельцев.
